## ■ 3. 判定

### 【判定77】**① r4 で直してから V2 を行う**（AIスライドのおすすめを採用）
- 理由：①r3 のままだと、AI が説明どおり `area` と書き、3枚目の「箇所」が空欄になる見込みが高い。V6 で入江さんが「欠け」と見て、合否の判断がぶれる ②**入江さんの V2 はまだ始まっていない**ので、今直しても入江さんの手戻りはない ③直すのは説明・見本・点検だけで、builder は変えない。
- 判定74「V2〜V6 で使う版は r3 で確定」は、**r4 に置き換える**。r3 の zip は消さずに保存する。

### 【判定78】r4 の直す範囲（builder 本体は変えない＝判定58-2）
1. **`input_schema.md`**：highlights を `{title, target_area, priority, effort, before, after}` に直す。1行で「**target_area・priority・effort は、C-2 の対応する改善提案と同じ値を使う**」と書く。上限は builder に合わせる（target_area は20字で切られるため「20字以内」）。
2. **`flow_summary` を追加**（C-3 の項目に1行）：「行動フローのまとめ（40字以内・1文）」。必須にするかは次のとおり：**入れることを推奨**（無くても点検で不合格にはしない）。
   - 理由：GPTs の出力にあった欄かどうかを統括は確認できていない。AIスライドは過去の GPTs の出力（7月のドッグフーディング）で、この欄が出ていたかを確かめ、**出ていたなら必須に上げる**（その場合は点検にも入れる）。結果を r4 の記録に書くこと。
3. **見本 JSON**：上の2点を反映（target_area・priority・effort を C-2 の提案と一致させる。flow_summary を1文入れる）。
4. **`check_output.py`**：次の2点を追加。
   - highlights の各件に **`target_area` が空でなく入っている**こと（`area` だけのときは「area ではなく target_area と書く」と表示）
   - C-3 の PPTX の中に、各件の「**箇所：{target_area}**」があること（PPTX との照合・判定68 と同じ考え方）
   - `priority`・`effort` は**入っていることだけ**を点検する（「高・中・低」「小・中・大」のどれか）。C-2 との一致までは点検しない（言い換えのゆらぎで止まりすぎるため）。
5. 試験：r3 の見本（`area` のまま）で**不合格**になること／r4 の見本で**合格**すること／PPTX を作り直さずに JSON だけ `target_area` を足したときに**不合格**になること。t1〜t11 は引き続きすべて不合格のまま。
6. zip：r4 として新しい名前で置き、中身一覧（B・md5）を記録。**統括の事後確認方式**（判定73）を r4 にも使ってよい（上の試験が全部とおれば、統括の再審査を待たずに入江さんへ渡してよい）。

### 【判定79】PLAIN の誤記と、今の GPTs の扱い
- **PLAIN（採用版）は直さない**（今は凍結中で、GPTs の更新はしない）。468行の `area` は誤記として**台帳に記録**する（SCRIPTS_REGISTRY か変更履歴に1行）。
- 今の GPTs でも3枚目の「箇所」が空欄になりうることは、**既知の不具合として記録**する。GPTs は12/11で終わり、販売の主軸はスキル版に移ったため、GPTs 側の修正はしない。
