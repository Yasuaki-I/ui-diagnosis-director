## 1. 設計メモへの補足（判定213-3）

### 1-1. 「成果が出る」を、目指す質と検証済みの効果に分ける（213-3①）
- 元の §1-1 の「そのまま実施しても成果が出るレベル」は、**目指す質**として扱う
- 資料の完成条件や、提供時の保証には使わない
- 書き方：**「実施を検討できる具体性を目指す。成果への寄与は仮説であり、実施後の検証を要する」**
- 資料の中でも、改善案の効果は「見込み（仮説）」と書き、確定した効果のようには書かない

### 1-2. 見えていないことを診断しない（213-3②）
- M1 の基準表の各項目に、**観察根拠・解釈・提案・評価**の4つを必ず含める（§2）
- 次のことを明記する：
  - **PC の画像だけから、スマホ表示を評価しない**
  - **保存した画像だけから、実際の操作や利用者の離脱を断定しない**
  - スマホ表示のページ（元の設計メモ §2 の10ページ目）などは、根拠となる資料がない場合は**省略するか「未評価」と書く**
- 元の設計メモ §2 の6ページ目「行動の流れと、止まる場所」は、画像から考えられる**推測**として書く。アクセス解析などの資料がない限り、「ここで離脱している」とは書かない

### 1-3. 点数を使う場合は、採点方法を説明する（213-3③）
点数を使うかどうかは、M1 で決める方針のまま。検討するときは、次のすべてを決める。
1. 各段階の採点基準（何があれば何点か）と、その配点にした理由
2. **対象外・未確認を0点と混同しない**扱い（例：「—」「未評価」と書き、合計に入れない）
3. 総合点の分母・重み・集計方法
4. 〇△×などより点数の方が読み手の判断に役立つ理由
- 基準が成り立たない項目は、無理に数字にしない
- 現行の評価方式（r6.2）を変える判断とは分ける

### 1-4. 優先順位と実装の手間には、根拠の確かさを示す（213-3④）
- 「効果の見込み×手間」は、**候補を整理する方法**として扱う。数字の掛け算や、確定した順位を前提にしない
- アクセス解析・利用者調査・実装の条件などがない場合、効果と工数は**未確認**と書く
- 根拠が足りない場合は、**順位を保留する／同じ順位にする／先に追加調査をする**という選択も認める
- 優先順位の判断表（元の設計メモ §2 の11ページ目）には、順位ごとに「根拠の確かさ」（例：画像で確認済み／推測／未確認）を添える

## 2. M1 で作る基準表の項目案（判定213-3②・213-5）
> 項目の「案」であり、基準表そのものではない。中身（採点基準・判定のしかた）は M1 で作り、統括の審査を受ける

### 2-1. 基準表の列（1行＝1つの評価項目）
| 区分 | 列 | 書く内容 |
|---|---|---|
| 観察根拠 | 出典 | どの資料か（例：B-4 の保存 PDF、ファイル名・識別値） |
| | 対象箇所 | 画面のどこか（ページ・位置・切り出し画像の名前） |
| | 取得条件 | 取得日時、画面の幅（PC／スマホ）、取得方法（保存 PDF・画面の画像など） |
| | 確認できた事実 | 画像で見えること。見えないことは「見えない」と書く（「無い」と断定しない） |
| 解釈 | 想定する利用者・目的 | 誰が、何のためにそのページを使うと想定したか |
| | 課題と考える理由 | なぜ課題と考えるか |
| | 推測の範囲 | どこからが推測か。何があれば確かめられるか |
| 提案 | 改善案 | 直し方の方向 |
| | 前提条件 | その案が成り立つ条件（例：手続きの一覧データがあること） |
| | 追加確認が必要な点 | 実施の前に確かめること |
| 評価 | 判定基準 | 〇△×（または点数）にする条件 |
| | 根拠との対応 | 判定がどの事実に基づくか |
| | 判定 | 〇△×／点数／**未評価**／**対象外** |
| | 未確認・対象外の扱い | 合計に入れない、理由を書く、など |
| 優先順位 | 効果の見込み | 仮説として書く。根拠の確かさを添える |
| | 手間の見込み | 分からない場合は「未確認」 |
| | 順位の扱い | 順位／同順位／保留（理由つき） |

### 2-2. 評価項目の候補（見本ボードの10項目を出発点にした案）
| # | 評価項目の候補 | 保存画像だけで判定できる範囲 | 判定できないこと（未評価・対象外にする） |
|:-:|---|---|---|
| 1 | 構成・情報の順番 | ページ内の並び | 利用者が実際に読む順番 |
| 2 | 行動の入口（ボタン・リンク）の分かりやすさ | 位置・文言・目立ち方 | クリックされているか |
| 3 | 文字の読みやすさ | 大きさ・行の長さ・コントラスト（画像上） | 実機での見え方 |
| 4 | 配色の役割 | 色の使い分けの一貫性 | ブランドの方針との整合（資料がない場合） |
| 5 | 見出し・情報のまとまり | 見出しの有無・階層 | — |
| 6 | 内容の分かりやすさ | 文言・説明の有無 | 内容の正しさ（業務の資料がない場合） |
| 7 | 信頼を支える情報 | 実績・問い合わせ先などの表示 | 情報が正しいか |
| 8 | 検索・案内の仕組み | 検索欄・入力例・ナビゲーションの表示 | 検索の結果の質 |
| 9 | スマホ表示 | **スマホ幅の画像がある場合だけ** | PC 画像しかない場合は全体を未評価 |
| 10 | 表示速度・操作の動き | — | 保存画像では判定できない。対象外 |
- 項目の採否・名前・数は M1 で決める。見本ボードの10項目をそのまま使うことは前提にしない

### 2-3. M1 の机上適用（判定213-4・213-5）
- 対象：4件目（大田区「よくある手続き」）の保存資料
- **明確な例**と、**根拠不足で採点・順位を保留する例**の両方を机上で説明する
  - 明確な例の候補：分類の枠に分類名だけが並んでいる（画像で見える）
  - 保留する例の候補：オンライン申請の入口（このページの画像だけでは有無を確かめられない）、スマホ表示（スマホ幅の資料がない）
- 机上適用は新しい評価基準の検討であり、**大田区の既存の確定評価（4件目の確定版・判定196・197）を書き換えない**

## 3. ページ構成とマイルストーンへの補足（判定213-4）
### 3-1. ページ構成
- 10〜12ページは**目安**。上限や固定の枚数にはしない。読める画像・文字と、論理のつながりを優先する
- 「30秒で要点が分かる」は**設計目標**であり、達成を確かめたものではない

### 3-2. 各段階の終わりの条件（具体化）
| 段階 | 終わりの条件に加えること |
|---|---|
| M1 | 明確な例だけでなく、根拠不足で採点・順位を保留する例も机上で説明する |
| M2 | 「画像の中の文字が読める」と「改善の理由が分かる」を**別の項目**で評価する。〇の条件と確かめ方は試験の前に決める |
| M3 | 構造マップ・評価のまとめ・行動の流れが、**同じ根拠を参照して矛盾なく対応しているか**を確かめる |
| M4a／M4b | 見た目の作り込みと、コードでの実装を分ける。**M4b を行うこと自体は、LP 生成・公開の承認ではない** |
| M5 | 「2回で品質がそろう」だけで、一般的な再現性を実証したとはしない。入力・条件・評価項目・許容する差を事前に決める |
| M6 | 人数・対象者・質問・成功条件・「資料だけで読む」条件を事前に決める。印象だけでなく、**何を理解し、何を判断できたか**を見る |
| M7 | 組み込むかどうかと、凍結を解くかどうかを**別々に判断する**。M6 を通っても自動的には解除しない |
- 試験1で残った「改善理由の訴求力・優先順位」は、試験1の合否には足さない。今後の試験で、事前に決める評価項目として扱う
