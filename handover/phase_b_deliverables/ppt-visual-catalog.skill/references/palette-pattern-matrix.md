## 📌 章1｜7×12=84マトリクスの分類ルール確認

### 分類ルール

| 記号 | 名称 | 定義 |
|------|------|------|
| `●` | 推奨組み合わせ | 診断結果カテゴリとテーマ選定条件が両方合致する場合に即採用可能／代表組み合わせ候補 |
| `○` | 条件付き採用 | 診断結果の強調度合いによって採用／基本は代替候補を優先 |
| `△` | 予約枠 | v3.5時点は非採用／Phase C以降で診断項目拡張時に発火予定 |

### 分類の判断軸（3軸）

1. **色トーンと診断結果カテゴリの意味的整合**（例：Red は警告色 → `contrast`／`funnel`で発火）
2. **色トーンとプロジェクトタイプの相性**（例：Blue はコーポレート／BtoB向け）
3. **Phase A A-2 `DIAGNOSIS_TO_PATTERN` マッピングの有無**（`integration` は11マッピング外 → 7組すべて △）

## 📊 章2｜プロジェクトタイプ × テーマ 推奨マトリクス（テーマ選定の根拠）

診断対象サイトのプロジェクトタイプに応じて、まず**テーマ**を絞り込む。本表は「どのプロジェクトタイプにどのテーマが適するか」の一次判定：

| テーマ ＼ プロジェクトタイプ | コーポレート | EC | LP | Webアプリ | メディア／ブログ |
|--------------------------|-----------|-----|-----|---------|-------------|
| SolidGray | ◎ | ○ | ○ | ○ | ○ |
| Blue | ◎ | ○ | ○ | ○ | △ |
| LightBlue | ○ | ○ | ○ | ◎ | ○ |
| Green | △ | △ | △ | ○ | ◎ |
| Cyan | △ | △ | △ | ◎ | ○ |
| Red | △ | ○ | ◎ | △ | △ |
| Orange | △ | ◎ | ◎ | △ | △ |

**凡例**：◎=最推奨／○=標準採用／△=非推奨（強調意図がない限り不採用）

### テーマ選定の判断根拠（1行サマリ）

| テーマ | 判断根拠（色トーンとプロジェクト特性の合致点） |
|-------|--------------------------------------------|
| SolidGray | 中立・客観・全プロジェクトタイプで安全に使える万能テーマ／コーポレートで最推奨 |
| Blue | 信頼・企業的印象／コーポレート・BtoBサイトの診断結果に最適 |
| LightBlue | 清涼・IT感／Webアプリ・SaaSダッシュボードの診断結果に最適 |
| Green | 成長・自然・持続性／メディア・ブログの継続改善提案に最適 |
| Cyan | 技術・革新感／Webアプリの機能訴求ある診断結果に最適 |
| Red | 警告・強調／Good/Bad対比・緊急改善提案時のみ限定発火 |
| Orange | 活力・行動・CTA連想／LP・ECのCVR最適化診断に最適 |

**検証ステップ**：診断対象サイトのプロジェクトタイプを最初に確定し、本表◎／○のテーマから2〜3候補に絞り込む。その後、章3の推奨判定表で最終組み合わせを確定する。

## 🌟 章4｜代表組み合わせ15組 詳細判断根拠

各代表組み合わせに対し、以下5フィールドで根拠を明記する：
1. 選定根拠
2. 診断カテゴリ／プロジェクトタイプ
3. 数値位置踏込
4. 検証ステップ
5. 代替候補（不採用時の切替先）

### 代表組み合わせ #1｜SolidGray × category

| フィールド | 内容 |
|-----------|------|
| **選定根拠** | 中立トーン×並列カテゴリ整理は、プロジェクトタイプに依存しない万能組み合わせ。診断結果の提案項目を評価バイアスなく整理する第一選択 |
| **診断カテゴリ／プロジェクトタイプ** | `proposal_categorization` × 全タイプ共通 |
| **数値位置踏込** | 要素数 4〜12個／グリッド段数 2〜3段／最小フォント 14pt（1280×720キャンバス基準） |
| **検証ステップ** | 要素数上限12を超えていないか／グリッド段数が2〜3段の範囲内か／各要素サイズが均等（±5%以内）か |
| **代替候補** | Blue × category（コーポレート強調時）／LightBlue × category（Webアプリ強調時） |

### 代表組み合わせ #2｜Blue × breakdown

| フィールド | 内容 |
|-----------|------|
| **選定根拠** | 企業的トーン×構造分解／10項目スコア内訳を信頼感を持って提示。BtoB・コーポレート診断結果の中核組み合わせ |
| **診断カテゴリ／プロジェクトタイプ** | `score_breakdown` × コーポレート／BtoB |
| **数値位置踏込** | 階層数 2〜3層／子ノード数 2〜7個／ノード間垂直間隔 キャンバス高さの8〜12%／最小フォント 12pt |
| **検証ステップ** | 階層数が3層以内か／子ノード数がMiller's Law範囲内（7±2）か／エッジ交差がないか |
| **代替候補** | Cyan × breakdown（技術系強調時・代表組み合わせ #14）／SolidGray × breakdown（中立表現時） |

## 🔀 章5｜条件付き採用（○）14セルの発火条件

条件付き採用14セルを、発火条件別に分類する：

### 分類A｜「中立性 vs トーン」の緊張関係で条件付き（4セル）
- SolidGray × cycle：循環は成長・生命感が本質 → Green cycle優先が原則、中立表現必要時のみ SolidGray 発火
- SolidGray × funnel：絞り込みは活力・警告が本質 → Orange/Red funnel優先、中立表現必要時のみ SolidGray 発火
- Green × contrast：Good/Bad強調は警告色が本質 → Red contrast優先、成長トーンで穏やか表現時のみ Green 発火
- Green × framework：2軸評価は企業感が本質 → Blue framework優先、メディア文脈で穏やか表現時のみ Green 発火

### 分類B｜「技術性 vs 中立性」の緊張関係で条件付き（4セル）
- Cyan × category：並列カテゴリは中立性が本質 → SolidGray/LightBlue優先、技術系サービスカテゴリ強調時のみ Cyan 発火
- Cyan × funnel：絞り込みは活力・警告が本質 → Orange/Red優先、技術系サービスファネル強調時のみ Cyan 発火
- Cyan × contrast：Good/Bad強調は警告色が本質 → Red優先、技術系UI対比時のみ Cyan 発火
- Cyan × framework：2軸評価は企業感が本質 → Blue優先、技術系評価軸強調時のみ Cyan 発火

### 分類C｜「警告色 vs 中立性」の緊張関係で条件付き（3セル）
- Red × category：並列カテゴリは中立性が本質 → SolidGray優先、緊急対応カテゴリ整理時のみ Red 発火
- Red × cycle：循環は反復性が本質 → Green優先、緊急改善サイクル訴求時のみ Red 発火
- Red × network：多対多関係は中立性が本質 → LightBlue優先、緊急対応ネットワーク訴求時のみ Red 発火

### 分類D｜「活力色 vs 中立性」の緊張関係で条件付き（3セル）
- Orange × category：並列カテゴリは中立性が本質 → SolidGray優先、LP・EC商品カテゴリ強調時のみ Orange 発火
- Orange × cycle：循環は成長・生命感が本質 → Green優先、LP・EC継続利用訴求時のみ Orange 発火
- Orange × network：多対多関係は中立性が本質 → LightBlue優先、LP・EC商品ネットワーク訴求時のみ Orange 発火

### 条件付き採用の運用ルール

**発火順序**：
1. まず本カタログ推奨表で `●` の組み合わせを検討
2. `●` に該当しない場合、`○` の条件付き採用を検討
3. 条件付き採用の「発火条件」が満たされる場合のみ採用
4. どちらも該当しない場合、代替候補（本章の分類A〜D記載）に切替

**検証ステップ**：条件付き採用を発火させた場合、その診断結果PPT出力の脚注に「本組み合わせは条件付き採用（○）／発火根拠：〜」を明記する。ログトレーサビリティを担保する。
