## 🌳 選定フロー（診断結果 → 組み合わせ自動選定）

以下のフローで、診断結果から最適な組み合わせを自動選定する。

```
[診断結果カテゴリID] × [プロジェクトタイプ]
    │
    ├─ ステップ1｜B-3の DIAGNOSIS_TO_PATTERN で図解パターンを確定
    │       │
    │       └─ 例：conversion_funnel → funnel パターン
    │
    ├─ ステップ2｜プロジェクトタイプに応じてテーマを選定
    │       │
    │       ├─ コーポレート／BtoB → Blue / SolidGray
    │       ├─ Webアプリ／SaaS → LightBlue / Cyan
    │       ├─ メディア／ブログ → Green
    │       ├─ LP／EC → Orange（強調時Red）
    │       └─ 全タイプ共通 → SolidGray
    │
    ├─ ステップ3｜本カタログの推奨表（`●`/`○`/`△`）で採用可否確認
    │       │
    │       ├─ `●` → 即採用
    │       ├─ `○` → 診断結果の強調度合いで判定（強調不要ならNG）
    │       └─ `△` → 予約枠（v3.5時点は非採用・代替組み合わせを検討）
    │
    └─ ステップ4｜B-3の「使うべき条件」数値基準を満たすか確認
            │
            ├─ 満たす → 描画実行
            └─ 満たさない → 代替組み合わせ（本カタログ／B-3を参照）へ差し替え
```

## 💰 Brain販売原稿での訴求ポイント（拡張5層第5層接続）

拡張5層のうち第5層「レイアウト・フォント設計思想（7テーマ×8色階調・12種図解パターン）」の **組み合わせ側面** を、以下3層で訴求する：

### 訴求層1｜「7×12=84パターン組み合わせ内蔵」の網羅性訴求
- Phase A A-1（7テーマ）× A-2（12種パターン）＝ **84組み合わせすべて実装済み**（辞書レベル・v3.5時点）
- そのうち **63組（75%）が推奨組み合わせ** として即採用可能
- 診断結果カテゴリ×プロジェクトタイプに応じて **自動で最適組み合わせが選定される**

### 訴求層2｜「判断基準の透明性」訴求
- 各代表組み合わせに「なぜこのテーマ×このパターンを推奨するか」を明文化
- 誤用防止のガード（条件付き採用○・予約枠△）を明示
- **他社ツール差別化**：「なぜその組み合わせを選んだか」の根拠を診断結果とセットで提示可能

### 訴求層3｜「拡張余地の設計」訴求
- `integration` 予約枠（7組）を保持し、将来の診断項目拡張に対応可能
- 診断カテゴリ追加時、本カタログへの推奨組み合わせ追記のみで対応可能
- **設計の持続性**：v3.5 → v3.6 → v4.0 への進化余地を確保

**訴求時の attribution 遵守**：
- テーマID・パターンID・診断カテゴリIDの実名列挙は **内部技術文書（本スキル・B-3）内に限定**
- Brain販売原稿・note・X等の発信では **抽象表現**（「7テーマ×12種パターン＝84組み合わせの自動選定」等）に留める
- `attribution_policy_20260727_rev2.md` の運用ルール遵守
