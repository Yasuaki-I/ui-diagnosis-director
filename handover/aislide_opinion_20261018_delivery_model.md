## A. 方式
### Q1　Agent Skills 形式の1フォルダにそろえる ＝ **賛成**
- 理由：①中身が1つなので、版の管理と検証が1系統で済む ②SKILL.md は ChatGPT のプロジェクトの指示欄にもそのまま貼れるので、私の案（ChatGPT のプロジェクトに組み立てる）は**損なわれない**（入れ方の1つとして残る）③lite の 8,000字の制約から外れる
- 損なわれうる点（2つ）：
  1. **起動の確実さ**：GPT は「開けば必ずこの指示で動く」が、スキルは AI が自動で選ぶ（選ばれない場合がある｜判定50）。→ README に「名前で呼び出す」1行を必ず書く（判定52-4 に賛成）
  2. **同じ会話の中の他の指示との干渉**：GPT は専用の場だったが、スキルは購入者のふだんの会話に混ざる。→ README で「新しいチャットで始める」を手順の1番目にする

### Q2　「置くだけ」と「誰でも使える」の両立 ＝ **条件付きで両立できる（定義を変えれば）**
- Codex（置くだけ）は、ターミナルや IDE を使う人向けの道具で、Web 担当者・個人事業主・副業の方には向かないと見る（この層は「フォルダの所定の場所」が分からない）
- 両立のしかた：入江さんの「置くだけ」を、購入者の操作として「**zip を1回アップロードして、設定を1つオンにするだけ**」と読み替える。Claude の Customize > Skills はこれに当たる（判定50 事実1・2）。Python のインストールもフォルダの場所の理解も要らない
- 🔴 ただし「1回アップロードで済む」は公式の記述であって、**実機では未確認**（V2 で確かめる）

### Q3　主軸の環境を1つ選ぶなら ＝ **Claude**
- 理由：①個人の Free プランから自分のスキルを入れられる、と公式に書かれている唯一の環境（事実1）②ファイル作成（.pptx）が公式機能（事実2）③画面の操作だけで完結し、購入者の層（技術に慣れていない方が多い想定）に合う
- 弱点：①購入者の多くは ChatGPT に慣れていて、Claude のアカウント作成が「一手間」になる ②Free の利用枠で、ヒアリング→確認A/B→生成の長い対話が途中で止まる可能性（**未確認**｜V5）
- ChatGPT は「対応環境の2番目」に置く。利用者数は最も多いが、プロジェクトの `/mnt/data` 不具合（事実7）が残る限り主軸にはしない

## B. 技術
### Q4　builder の読込み ＝ **2行方式はそのまま使える（手元で確認済み）。置き場所は「探す」手順を足す**
- 手元の確認：`scripts/03_pptx_builder.py` を相対パスで読み、2行方式（`_ns = {'__name__': 'pptx_builder'}; exec(...)`＋`globals().update(...)`）で4関数が使えた。デモは動かず `test_*.pptx` は0件
- より安全な書き方（SKILL.md に書く手順の案）：
  1. 置き場所の候補を順に探す（スキルフォルダの `scripts/` → 作業フォルダ → 見つからなければ `03_pptx_builder.py` という名前でファイルを検索）
  2. 見つけたら、**場所と版（`__version__`＝17.2.17）を購入者に1行で報告**してから使う
  3. 見つからなければ生成に進まず、「builder が見つからない」と伝える（勝手に python-pptx で作り直さない＝J-0 の継承）
- 2行方式と importlib の選び方：どちらも動いた。**SKILL.md では2行方式を既定**とする（GPTs で検証済みの方式で、R-7 対策の実績がある）
- 🔴 Claude のスキルが実行環境の**どの場所に置かれるか**は未確認（V2 で、AI に場所を報告させて記録する）

### Q5　python-pptx が使えるか ＝ **未確認**
- 把握している範囲：作業領域には python-pptx 1.0.2 がある。Claude・ChatGPT の実行環境に**最初から入っているかは確認できていない**。ネットワークが切られた環境では、後から導入できない可能性がある（統括の指摘どおり）
- 確かめ方：V2・V3 の最初の操作として、診断の前に AI へ「`import pptx; print(pptx.__version__)` を実行して結果を教えて」と頼む（30秒で済む）。入っていなければ、その時点で検証を止めて記録する
- 入っていない場合の扱い：その環境は「対応」にしない（購入者に導入を求めると、環境構築の容易さという最優先の条件に反する）

### Q6　フォント（メイリオ） ＝ **対処は要る（注意書きと確認1回）**
- 前提の整理：builder の文字幅の判定は、内部の実測表（メイリオの幅）で行っている。つまり**生成する環境にメイリオが無くても、配置は崩れない**。崩れうるのは**購入者が開いて表示するとき**だけ
- Windows は標準でメイリオがある。Mac の PowerPoint・Keynote・Google スライドで開いたとき、メイリオが入っているかは**未確認**
- 対処案：①販売ページと README に「Windows の PowerPoint での表示を基準に作っています」と1行 ②Mac で開いた見え方を、入江さん（または協力者）が1回確認（V2 の生成物を使う・任意）③代替フォントの指定は**しない**（14pt 判定・重複ゼロの実測根拠が変わり、builder 本体の改版になるため）

### Q7　機能の網羅と、長さの心配 ＝ **条件付き賛成（長くしすぎない・点検は機械で）**
- 見込み：流れ（ヒアリング2問・確認A/B・承認後に生成）は**守られる見込みが高い**。ただし AI ごとの差が最も出やすいのは「字数・件数」（総評17字・S/A/B=3 など）
- 長さの心配：**ある**。手順が長いほど、どの AI でも後半の規則が守られにくくなる。→ SKILL.md は lite と同じくらいの長さに抑え、細目は references/ に逃がす
- 🆕 総評17字の「自動やり直し」は、GPT ではプロンプトで担っていた。これを **`scripts/check_output.py`** に移す：生成後に AI が実行 → 総評の字数・件数・ファイル名・`test_*.pptx` の有無・リンクの有無を点検 → 不合格なら AI が直して再生成。どの AI でも同じ基準で止まる
- 切り分け案：
| 置き場 | 入れるもの |
|---|---|
| `SKILL.md`（必ず読まれる） | いつ使うか（description）／3ステップと「待った」2か所／必須2項目と仮置き／10項目と5段階・ランク・件数・主要な字数／builder の読込み手順（Q4）／生成後に check_output.py を実行すること／やらないこと（J-0・K） |
| `references/` | 採点の判断例・タイプ判定の細目／入力データの項目一覧（schema）／図解パターン（J-7）の仕様／納品メッセージ・深掘り提案の雛形／エラー時の文面（E1〜E4） |
| `scripts/` | `03_pptx_builder.py`（採用版・無改変）／`check_output.py`（新規） |
| `assets/` | 入力データの雛形（JSON）／完成例の小さな見本（任意） |

## C. 商品と区分
### Q8　再配布の対策 ＝ **追加の対策は要る（ただし技術で防ぐことはできない）**
- ファイルとして手元に残る以上、コピーを技術的に止める方法は無い。抑止と、見つけたときの根拠づくりに絞る
- 対策案：①SKILL.md・README・builder の先頭に「購入者限定・再配布・転載・転売禁止」の短い表記（判定19 の文面を使う）②販売ページの購入前注意（827行）は現行の文面のまま ③版の表記（`__version__` と同梱物の版）で、出回ったものがどの版か分かるようにする
- やらないこと（推し）：購入者ごとの識別情報の埋め込み（Brain の配布の仕組みでは、購入者ごとに別ファイルを渡せない可能性が高い｜未確認）・難読化（builder の検証済みの状態が変わる）

### Q9　販売ページの書き換え範囲 ＝ **概算で10節前後・40〜60行**（原稿 r2 1,177行に対し）
